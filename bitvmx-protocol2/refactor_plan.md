# BitVMX 프로토콜 리팩토링 계획

## 현재 구조의 문제점

1. **온체인에 너무 많은 데이터**: 옵션 데이터를 직접 트랜잭션에 포함
2. **BitVMX 철학 위반**: Commitment 방식을 제대로 활용하지 못함
3. **비효율적인 검증**: 전체 트레이스를 온체인에 올리려 함

## 올바른 아키텍처

```
┌─────────────────────────────────────┐
│      웹서비스 레이어 (오프체인)         │
│  - 옵션 등록/구매/조회 API            │
│  - PostgreSQL/MongoDB                │
└────────────┬────────────────────────┘
             │
┌────────────▼────────────────────────┐
│      계산 레이어 (오프체인)           │
│  - Black-Scholes 가격 계산           │
│  - 정산금 계산                       │
│  - 실행 트레이스 생성                 │
└────────────┬────────────────────────┘
             │
┌────────────▼────────────────────────┐
│     BitVMX 레이어 (검증)             │
│  - 32바이트 Commitment 생성          │
│  - Merkle Tree 구성                  │
│  - Challenge/Response 준비           │
└────────────┬────────────────────────┘
             │
┌────────────▼────────────────────────┐
│      Bitcoin Network (온체인)        │
│  - Funding TX                        │
│  - Prover TX (32바이트 커밋만)        │
│  - Settlement TX                     │
│  - (분쟁 시) Challenge/Response TX   │
└─────────────────────────────────────┘
```

## 수정 작업 단계

### Phase 1: 서비스 레이어 구현
1. FastAPI 기반 REST API 서버
2. 옵션 상품 CRUD
3. 구매 내역 관리
4. 만기 옵션 스케줄러

### Phase 2: 계산 엔진 분리
1. 옵션 가격 계산 모듈
2. 정산금 계산 로직
3. RISC-V 프로그램 생성
4. 실행 트레이스 생성

### Phase 3: BitVMX 통합
1. Commitment 생성 (32바이트)
2. Merkle Tree 구성
3. Challenge/Response 트랜잭션 준비
4. 정산 트랜잭션 생성

### Phase 4: 온체인 최소화
1. Funding TX - 초기 자금만
2. Prover TX - Commitment 해시만
3. Settlement TX - 정산 실행
4. Challenge TX - 분쟁 시에만

## 핵심 원칙

1. **오프체인 최대화**: 모든 계산과 데이터는 오프체인
2. **온체인 최소화**: 32바이트 커밋과 정산만
3. **검증 가능성**: 분쟁 시 증명 가능
4. **확장성**: 수천 개 옵션도 처리 가능

## 예상 결과

- **온체인 데이터**: 기존 수 MB → 32바이트
- **가스비**: 90% 절감
- **처리 속도**: 100배 향상
- **확장성**: 무제한 옵션 처리 가능
